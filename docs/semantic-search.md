# 의미 검색과 평가

## 달라지는 사용법

`/search`의 기본 **의미·단어 혼합** 모드에서는 핵심어를 미리 고르지 않고 질문 문장으로 원문을 찾을 수 있습니다. **단어 일치**와 **의미만 비교**도 선택할 수 있습니다. 자료 언어와 종류는 기존처럼 선택하며, 선택한 한 언어 안에서 검색합니다. 벡터 자료가 준비되지 않았거나 정책·원문·모델 버전이 맞지 않으면 혼합·의미 모드를 사용할 수 없습니다.

로컬 AI도 같은 모드를 사용합니다. 의미 검색에서는 AI 질문란에 쓴 문장으로 근거를 다시 찾습니다. 단어 검색에서는 위 검색어가 근거를 고릅니다. 답변은 상위 5개 묶음에 한정되며, 기본 화면에는 원문 일치 인용을 표시하고 해석은 미검증 상태로 접습니다.

## 공부할 개념

청킹은 긴 자료를 원문 위치가 있는 작은 묶음으로 나누는 것입니다. 임베딩은 그 묶음과 질문을 숫자 배열로 나타내는 것입니다. 비슷한 배열을 가까운 순위로 찾으면 다른 표현을 쓴 문장도 검색할 가능성이 생깁니다. 태그 붙이기나 모델 재학습과는 다릅니다.

RAG는 검색 결과를 모델에 읽혀 출처를 바탕으로 답하게 하는 과정입니다. 검색이 관련 원문을 못 찾으면 답변도 놓치기 쉽습니다. 검색에 성공했다고 모델이 올바르게 해석한 것은 아니고, 정확한 인용을 복사했다고 설명이 참인 것도 아닙니다.

## 왜 의미와 단어를 섞었나

한국어·영어가 먼저 완성된 시점의 예비 검사에서 의미만 비교하면 기대 근거를 상위 5개 안에 찾은 질문이 8/12개였습니다. 일부 짧은 대사·사실을 놓쳤습니다. 해당 표본의 저장 벡터를 새로 계산한 값과 대조해 일치함을 확인했으므로, 그 표본에서는 저장 손상이 아니라 검색 방식의 한계로 판단했습니다.

질문에 적힌 인물 이름과 드문 제목은 자료의 기존 정보와 연결하고, 그 이름을 잠시 뺀 주제 질문으로 해당 자료 안의 후보도 비교합니다. 전체 의미 순위·단어 단서 순위·지정 자료 안의 주제 순위를 RRF(여러 순위의 합성)로 섞습니다. 원문은 바꾸지 않으며 수동 주제 태그나 정답 문구를 검색 규칙에 넣는 방식이 아닙니다. 혼합 예비 결과는 11/12개였고 영어 악기 질문 1개는 여전히 놓쳤습니다.

이 질문들은 개선 과정에서 사용한 개발 세트입니다. 점수 상승을 보지 않은 질문 전체의 정확도 향상으로 단정할 수 없습니다. 영문 이름의 경계, 한국어 조사 보완, 한자·가나의 짧은 문자열 단서를 사용하는 휴리스틱도 완전한 언어 분석은 아닙니다. 혼합 점수나 유사도를 정답 확률로 읽으면 안 됩니다.

이번 구현은 [Qwen3-Embedding-0.6B](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)와 로컬 [Ollama 임베딩 API](https://docs.ollama.com/api/embed)를 사용합니다. 공식 Ollama 모델은 [qwen3-embedding:0.6b](https://ollama.com/library/qwen3-embedding:0.6b)입니다. 배포 정보의 Apache 2.0 라이선스를 확인했으며, 실제 설치 크기는 639,150,858바이트입니다. 모델 설명의 성능 수치는 이 프로젝트에서 측정한 성능이 아닙니다.

## 원문과 제외 기준 보호

- 검증된 `data/indexes/global-v1/`의 206,048개 청크만 벡터로 만듭니다. RAW나 전체 정규화 자료를 직접 검색하지 않습니다.
- `config/retrieval-policy.json`의 고정 글로벌 기준과 보류 항목을 유지합니다. 날짜가 지났다고 메인 17장 등을 자동 추가하지 않습니다.
- 제목·인물·본문을 임베딩 입력으로 쓰지만, 실제 결과는 기존 원문·화자·선택지 조건·출처·언어판 표시입니다.
- 동일 임베딩 입력은 계산을 공유해도 모든 출처 연결을 보존합니다. 기존과 같이 결과 화면에서만 동일 본문을 합칩니다.
- 벡터는 512차원의 정규화된 Float32입니다. 코사인 유사도로 후보를 정렬하고 최대 250개만 보여 줍니다. 점수를 정답 확률로 표시하지 않습니다.
- 모델은 지문으로 고정합니다. 실행 중 자동 다운로드·유료 API·원문 외부 전송은 하지 않습니다. 입력이 길면 몰래 잘라내는 대신 오류로 중단합니다.

## 이어서 생성하기와 새 자료 반영

`scripts/build-semantic-index.mjs`는 각 파일의 원문 해시·설정·입력·출처 연결을 기준으로 체크포인트를 만듭니다. 중단되면 같은 명령으로 마지막 지문 검증된 배치부터 이어집니다. 일부가 생성돼도 20개 파일 전체 검증 전에는 완료 상태로 표시하지 않습니다.

동시 생성기를 차단하는 PID 잠금을 사용합니다. 체크포인트와 실제 벡터 지문이 맞지 않으면 자동 통과시키지 않습니다. 손상된 파생 파일만 다시 만들 때는 `--rebuild=en_US/module`처럼 검증된 언어/종류를 명시합니다. 이 옵션은 해당 생성 벡터만 다시 만들고 원문은 수정하지 않습니다. 종료 요청 뒤에는 실제 종료를 확인해야 합니다. 이번 재개 시험에서는 이전 프로세스가 살아 있어 동시 쓰기가 발생했고 지문 검사가 충돌을 검출했습니다. 영어 모듈 벡터를 재생성하고 동시 생성 차단을 실제로 확인했습니다.

새 자료는 먼저 글로벌 범위 선택·원문 대조·청킹을 갱신하고 의미 검색 생성·검사를 다시 실행합니다. 바뀌지 않은 파일은 재사용하지만, 파일 내부의 임의 문서만 갱신하는 세밀한 증분 인덱스는 아닙니다. 자동 수집·출시 감시도 아닙니다.

`scripts/audit-semantic-index.mjs`는 모든 청크의 출처 연결을 원문 목록과 대조하고 파일 지문·벡터 개수·숫자 유효성·정규화·설치 모델 지문을 검사합니다. 이 검사는 내용의 의미 정확성을 인증하지 않습니다.

## 평가를 읽는 방법

개발용 질문은 `config/retrieval-evaluation.json`에 있습니다. 20개 질문은 8개 사실 묶음이며 그중 4개는 네 언어로 반복합니다. 모든 자료 종류가 순위에 경쟁하도록 평가합니다. 질문은 작성한 개발 세트이지 보지 않은 실제 사용 질문 전체를 대표하는 시험은 아닙니다.

1. 기대 인용이 지정한 원문 안에 실제로 있는지 먼저 확인합니다.
2. 기존 단어 검색에 질문 문장을 그대로 넣습니다.
3. 기존 단어 검색에 사람이 고른 핵심어를 넣습니다.
4. 의미만 비교와 의미·단어 혼합에는 같은 질문 문장을 넣습니다.
5. 네 방식 각각에서 기대 원문이 상위 5·20개에 있는지, 첫 근거가 몇 위인지 측정합니다.

기대 근거와 같은 문구가 있어도 다른 인물의 기록은 적중으로 보지 않습니다. 동일 인물·종류의 정확히 같은 인용만 동등 출처로 인정합니다. 보고서는 `data/reports/retrieval-baseline.json`, `retrieval-comparison.json`입니다. 첫 호출에는 자료 읽기·모델 초기 실행 비용이 섞일 수 있어 시간 수치를 일반 응답 시간으로 단정하지 않습니다.

대표 질문 20개에서 좋은 결과가 나와도 넓은 세계관 질문, 여러 장면 종합, 함정 질문, 언어별 번역 차이와 AI 설명의 정확성은 별도 검사가 필요합니다. 주제 태그와 완전한 분기 경로 해석은 이번 범위에 포함하지 않습니다.

## 2026-10-03 전체 생성·검색 평가 결과

네 언어 20개 파일, 206,048개 청크의 모든 출처 연결·벡터 지문·차원·개수·유효한 숫자·정규화를 검사해 통과했습니다. 동일 입력을 공유한 고유 벡터는 201,139개입니다. 최초 실행부터 오류 수정·재개를 포함한 생성 경과 시간은 5,651초(약 94분)이며, 이후 일반 검색 시간이 아닙니다.

| 방식 | 입력 | 기대 근거 상위 5개 | 상위 20개 |
| --- | --- | --- | --- |
| 단어 일치 | 질문 그대로 | 0/20 | 0/20 |
| 단어 일치 | 사람이 정리한 핵심어 | 17/20 | 20/20 |
| 의미만 비교 | 질문 그대로 | 12/20 | 13/20 |
| 의미·단어 혼합 | 질문 그대로 | 19/20 | 19/20 |

혼합 검색은 한국어 8/8·영어 3/4·일본어 4/4·중국어 4/4에서 상위 5개 근거를 찾았습니다. 놓친 영어 질문은 “Which instrument did Amiya tell the Doctor she resumed playing?”이며, 실제 대사는 원문 비교 화면에서 “I picked up the violin again.”으로 확인했습니다. 자료 누락이 아니라 이 질문에 대한 순위 실패입니다. 이는 작은 개발 세트의 검색 결과이지 95%의 일반 정답률이 아닙니다.

자동 테스트 67개, HTTP 검사 17건, 린트와 프로덕션 빌드를 통과했습니다. HTTP 검사에는 글로벌 보류 메인 17장 차단, 선택본 밖 자료를 반환하지 않기, 외부 브라우저 요청 차단, 마지막 후보 페이지와 잘못된 페이지 거부가 포함됩니다. 실제 브라우저에서 질문으로 한국어 대사를 찾고 같은 원문의 영어판으로 전환했습니다.

## 2026-10-03 로컬 AI 답변 시험은 완료하지 못함

`gemma4:12b`의 첫 질문에서 3분 제한을 넘겼습니다. 최초 시도는 모델 준비 중 연결이 취소됐고, 처리 배치를 256으로 줄인 재시험에서는 약 122초 뒤 준비됐지만 전체 응답은 3분 안에 오지 않았습니다. 준비된 모델로 다시 요청한 시도도 같은 제한을 넘겼습니다. 배치 변경이 문제를 해결했다고 주장하지 않습니다. 다른 앱을 종료하거나 Ollama의 전역 설정을 변경하지 않았습니다.

계획한 답변 시험은 긍정 질문 4개와 근거 없는 질문 1개였으나 **완료 응답 0개**입니다. 나머지 4개는 시험하지 못했습니다. 보고서 `data/reports/semantic-rag-evaluation.json`에는 실행 실패, 인용 검증 `null`, 의미 검증 `null`을 기록했습니다. 이전 실패 기록은 `semantic-rag-loading-failure.json`에 보존했습니다. 실패를 빈 답변 성공이나 인용 검사 통과로 세지 않습니다.

시간 초과 때는 검색을 별도로 쓸 수 있다는 안내를 표시하도록 했고, 다음 답변 요청을 막는 잠금이 해제되는지도 자동 검사했습니다. 브라우저에서 답변 요청을 취소하고 다시 본문 검색을 사용했습니다. 현재 완료된 기능은 질문 기반 원문 검색이며 로컬 AI 답변의 실행 지연·의미 정확성은 남은 과제입니다.

## 2026-10-04 실행 회복과 5문항 원문 대조

사용자가 게임을 하지 않는다고 알린 뒤, 같은 기본 설정으로 단독 질문과 RAG를 다시 시험했습니다. 최초 단독 호출은 114초에서 8.5초, 준비된 모델의 같은 질문은 9.2초에서 0.3초, 짧은 형식 시험은 3분 초과에서 2초로 줄었습니다. 검색 모델과 답변 모델을 함께 올린 실제 5개 근거 호출도 5.8초에 완료됐습니다. GPU 자원 경쟁이 큰 기여 요인일 가능성이 높아졌으나, 게임만 켜고 끈 통제 시험은 아니므로 단일 원인을 확정하지 않습니다. 진단용 GPU 분할·검색 모델 내리기 설정은 제품에 적용하지 않았습니다.

검색 서버를 기존 빌드로 다시 실행하고 준비 상태를 별도 호출로 확인했습니다. 이어서 기존 `gemma4:12b`·문맥 8,192·배치 256 설정으로 긍정 질문 4개와 근거 없는 질문 1개를 실행했습니다. 원본·검색 정책·프롬프트·모델 설정은 변경하지 않았습니다.

| 시험 | 전체 호출 시간 | 자동 검사와 수동 대조 |
| --- | --- | --- |
| 아미야의 리더 권한 | 8.7초 | 기대 출처 1위, 인용과 설명의 핵심 내용 일치 |
| 아미야가 다시 연습한 악기 | 3.1초 | 기대 출처 2위, 바이올린·비밀이라는 대사 일치 |
| 냐무가 책장 구석에서 찾은 물건 | 3.0초 | 기대 출처 1위, 주변 문맥과 드럼 스틱 설명 일치 |
| 영어 엑시아 모듈의 캔디 맛 | 3.1초 | 기대 출처 1위, 라즈베리 맛은 맞지만 부가 발언 연결 표현은 근거 불충분 |

전체 시간은 검색·자료 읽기·모델 호출을 포함하고, 모델 API가 보고한 생성 시간은 1.3~6.0초입니다. 첫 호출의 준비 상태·캐시·PC 부하가 섞이며 이후 모든 질문의 응답 시간을 보장하지 않습니다.

수동 검토는 `data/reports/semantic-rag-manual-review-20261004.json`에 원래 출력·검토 기준·보완 제안을 구분해 남겼습니다. 자동 의미 검증은 여전히 `null`이며 이 작은 개발 세트를 일반 정답률로 읽지 않습니다. 이전 실패 보고서는 `semantic-rag-evaluation-20261003T143013423Z.json`에 보존했습니다. 평가 도구는 원래 모델 출력과 실제 근거도 남기고, 보고서를 갱신하기 전에 이전 결과를 날짜별로 보존합니다.

다음은 인물 메타데이터와 발언자 구분, 잘못된 전제·부정·선택지 조건을 보는 별도 품질 평가입니다. 처음 보는 질문과 여러 장면 종합으로 검사를 확대하기 전에 이번 부가 표현 문제를 재현·보완해야 합니다. 평가 결과를 확인하지 않고 정답 문구를 검색 규칙에 추가하거나 원문 인용 검사를 느슨하게 하지 않습니다.

## 2026-10-04 발언자 보완과 15문항 품질 검사

`config/answer-quality-evaluation.json`에 기존 5문항·보완용 4문항·독립 검사 6문항을 먼저 고정했습니다. 변경 전 개발 9문항을 실행한 뒤 일반 답변 지시와 근거 형식을 보완했습니다. 제목·groupName을 `metadata`로 구분하고, 관련 인물이 실제 화자를 뜻하지 않음·호칭과 발언자 구분·조건/부정 보존·잘못된 전제 수정·uncertainty에도 추측 금지를 명시했습니다. 특정 인물·정답을 제품 규칙에 넣지 않았습니다.

원래 영어 맛 질문에서 `Exusiai가 언급한`이라는 이름은 빠졌습니다. 하지만 한국어의 ‘르무엘 학생’ 호칭 질문은 uncertainty에서 계속 엑시아를 화자로 추측했습니다. 모형총 질문은 반복 기호·구두점이 다른 인용으로 설명이 거부됐습니다. 독립 검사에서는 출신지를 맞게 답한 뒤 ‘정보가 부족하다’고 하거나, 미래 대사를 맞게 설명한 뒤 과거/미래 구분이 불명확하다고 하는 모순 2개가 나왔습니다. 따라서 **품질 검사는 전체 통과가 아닙니다.** 중국어 이름·영어 용어의 한국어 표현도 공식 대응 이름을 검증한 결과가 아닙니다.
